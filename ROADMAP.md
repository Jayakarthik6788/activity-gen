# 9-Month GitHub Portfolio Roadmap

**Period:** 23 November 2026 – 23 August 2027  
**Targets:** 350+ genuine GitHub contributions and at least 35 consecutive active weeks.

This roadmap is a work plan, not a contribution generator. Only work that is actually completed should be committed or recorded. No backdating, empty commits, copied activity, or artificial commit splitting.

## Targets and pace

- 350+ qualifying contributions across the 9-month period.
- Maintain activity in at least 35 consecutive GitHub contribution weeks.
- Aim for 10–12 meaningful contribution events per week, with roughly 9 per week as the mathematical minimum across 39 weeks.
- Prioritize project quality: working features, bug fixes, tests, documentation, issue discussions, and reviewed pull requests.

GitHub's contribution graph has eligibility rules. Commits, pull requests, and issues do not all count in every circumstance, so check the profile graph rather than assuming every Git operation is counted.

## Weekly routine

| Day | Focus | Example evidence |
|---|---|---|
| Monday | Plan and inspect an existing project | Issue with acceptance criteria; reproduce a bug |
| Tuesday | Implement one focused change | Feature or bug-fix commit |
| Wednesday | Test and improve reliability | Unit/integration tests; CI fix |
| Thursday | Continue a portfolio project | Model, API, UI, or algorithm improvement |
| Friday | Review and document | README, usage example, architecture note |
| Saturday | Integrate and validate | Refactor, integration test, demo |
| Sunday | Review the week's work | Close completed issue; write a short progress note |

Do not force a commit every day. A smaller number of meaningful, reviewable changes is better than noisy history. Keep a sustainable weekly rhythm and protect the 35-week streak by doing real work regularly.

## Definition of a meaningful contribution

A contribution should have a clear purpose and verifiable outcome, such as:
- implementing or improving a feature;
- fixing a reproducible bug;
- adding tests that cover real behavior;
- improving CI or developer tooling;
- documenting actual setup, design, or usage;
- reviewing and responding to issues or pull requests.

Avoid empty commits, whitespace-only churn, arbitrary file edits, duplicated changes, and splitting one change into many commits solely to inflate counts.

## Weekly review checklist

- [ ] I completed and can explain the work I published.
- [ ] The change has a clear commit message and useful diff.
- [ ] Tests or manual verification were performed where appropriate.
- [ ] No secrets, credentials, or private data were committed.
- [ ] I checked the GitHub contribution graph and active-week streak.
- [ ] I selected the next small, achievable task.
